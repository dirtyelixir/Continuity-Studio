# Canonical shot state

## Ownership

`Shot.canonical_state` (`canonical-shot-state-v1`) is the sole authority for dynamic visual facts. It contains complete sets of atomic entity/fact keys at exact source times, authored transition intervals and frame composition records. Common dimensions include gaze_target, pose, position, held_props, expression, visibility, power, damage and custom object states. This is a generic model, with no character-name or gaze-specific branch.

JSON null means that a detail is unspecified at this time. It does not assert absence, a closed mouth or a physical transition. A known absence is an explicit string value such as `none`. A moment can record a mouth shape without inventing a duration for that shape. Every source includes 0, its duration, every required frame moment and transition boundaries. Additional semantic samples do not create pictures, cuts or generation segments.

`start_state`, `end_state`, interior `Frame.state` and all `Frame.description` fields remain compatible with the existing UI/export/renderer APIs, but they are compiled projections. `shot_state.compile_shot` overwrites them from canonical moments and exact-frame camera/composition data. Shot-level framing/camera prose can describe a later gesture or motion and is never pasted wholesale into each still. The compiler validates unique fact keys, consistent tracked dimensions, entity scope, exact frame bindings, source bounds, transition boundary values, overlapping changes and changes outside declared intervals. Unspecified observations are omitted from the rendering description.

Beat actions, blocking, expression summaries, scene direction and identity-canon prose remain readable context. They cannot revise canonical state. Their duplicated semantic claims are checked against the canonical timeline. New state decisions belong in canonical facts/transitions; composition decisions belong in canonical composition records. A model may retain old compatibility fields while editing canonical data; Studio recompiles them. A prose-only edit or removal of an existing canonical track is rejected.

## Pre-commit boundary

`engine.save_plan` is the only Production SQL writer. It validates source structure, checks the requested revision, prepares/compiles canonical state, independently checks semantics, then rechecks the revision and validates projections under the write lock before inserting either `projects.production` or `revisions`. Rejection happens before revision/asset/settings writes. Human artistic approval does not bypass this data-integrity gate.

`engine.finish` runs the same preparation before narrative/storyboard proposals become succeeded, including chapter pipelines, manual-result submission and recovered results. The canonical candidate is saved beside the original provider output. Direct edit, proposal adoption, chapter merge, restoration, image identity edits, editorial adoption/save, storyboard adoption and added endpoint frames all reach the shared gate. Chapter localization remaps canonical composition frame IDs. Board and editorial receipts are bound to the actual compiled plan, not the original pre-compilation candidate. Existing endpoint assets are not falsely restored to current after a legacy conversion changes their frame source.

The provider selected for the production is retained. Legacy extraction uses a typed StatePreparation response; the separate semantic check inspects the actual compiled candidate and original source scope. It checks all state dimensions, exact moments, beat timing and preservation of compatible composition. A generated legacy extraction can receive one same-provider structural repair using the exact validation error. An authored canonical decision or actual source conflict is not silently repaired. A revise/uncertain semantic result, unresolved structural error, contradictory authoritative input or provider error rejects the candidate. No media is submitted and no fallback provider is selected. A fully manual production provider currently requires configuring an automatic creative checker before this gate can complete; the system fails explicitly rather than inventing certification.

## Legacy migration and evidence

Historical SQLite revisions and provider/source snapshots remain unchanged. On the next formal write, legacy Shots are migrated with explicit authority: endpoint/interior state supplies specified dynamic facts, timed beats constrain their changes, and old frame prose supplies only compatible composition/detail. A stale prose clause is quoted in reconciliations. An actual state-versus-timeline conflict must fail; missing incidental details are represented as null. Restoration treats the chosen historical revision as its source and passes the same gate.

Preflight intent, source, extraction, compiled candidate, semantic verdict and reconciliation notes are stored under each job's `canonical-state` directory or `data/shot-state-checks/attempts/`. The original and compiled forms have content-addressed accepted receipts keyed by source scope, provider, compiler version and policy/schema. Successful adoption can reuse the exact check; changed source/context/provider/policy cannot. A failed or interrupted immutable job attempt cannot silently repeat. An explicit new save/job has a new attempt. Cancellation is checked before and after provider work. Same-input calls are serialized within the application; the final Production write retains optimistic concurrency checks.

`FRAME_MOMENT_SYNC` remains a rendering safety net and supports historical legacy inputs. It is not the normal authoring/synchronization mechanism. Current canonical frame contracts name the exact canonical moment as their state source. Image planning, conditioning, H3 and delivery receive compatible projections from the committed canonical Production; their instructions explicitly deny independent semantic authority to frame prose.

## Scope and limits

Deterministic compilation establishes identity between canonical state and its projections. The separate model check interprets arbitrary natural language; it is not a mathematical proof of all prose semantics or proof that rendered pixels follow a prompt. Media review remains separate. Canonicalization may invalidate source-bound media/review applicability; it preserves original files and receipts and never regenerates media automatically.

The portable Production schema and production contract include canonical state. They do not claim that JSON Schema alone implements the application's semantic pre-commit gate. Mandatory source method snapshots remain versioned independently.

Acceptance artifacts and the consumer/write-path audit are in `reviews/canonical-shot-state/`.

Outbound image-demand/grouping and H3 preparation contexts omit only reconstructible canonical projection fields. Full persisted snapshots and hashes are unchanged. Reused canonical board anchors may return blank description/state, which materialization fills from the exact committed canonical frame. This removes another model-authored copy and reduces context inflation.

When the same canonical source appears in multiple planner requirements, outbound context uses explicit shared libraries. `canonical_shot_ref` supplies shared Shot fields, with local keyframes retained; `canonical_state_ref` supplies the track. Each moment's ordered `state_refs` indexes complete entity/key/value records in that track's `fact_library`, preserving nulls and every snapshot exactly. Matching conditioning canon uses a root reference. This is a lossless wire representation, not omitted facts or interpolation; authored output still uses the normal full schema. The live full-source roundtrip is verified in the acceptance artifacts.


Canonical storyboard anchor purposes are source-time captions compiled by `storyboard_board.compile_result`; a planner cannot create a second frame-state description in that field. Raw provider output is retained, while the compiled candidate is saved separately. All remaining board summaries/reasons/planning notes receive an independent canonical semantic check before proposal success and again before adoption (with exact accepted-receipt reuse). Historical succeeded proposals cannot bypass that adoption gate. Interrupted/pending checks remain blocked; a new explicit job can retry without erasing the failed attempt. The explicit resume option can continue a pending transport/interruption check while archiving its prior receipt; it cannot retry a semantic revise verdict unchanged.
