# Automatic local image LoRA selection

New local image jobs use `studio-local-images-v6`. During the existing routed `image_prepare` call, the creative provider reads the full scoped still-image request and a frozen catalog of installed, reviewed, recipe-compatible adapters. It returns `local_lora_selection` with a Chinese summary and zero to two selected IDs, reasons and verbatim evidence from its returned visual fields. Astra remains the default; the configured alternative preparer can do the same job. There is no keyword-to-LoRA lookup and no additional creative-provider call in the normal image path.

Studio validates the decision, resolves exact filenames, fixed preset strengths and documented triggers, then freezes these in both `local_image_plan` and the provider plan before generation. Invalid/missing decisions, missing selected files, incompatible family/model, unknown IDs and changed resolved settings stop the job. Catalog changes invalidate preparation reuse for new local jobs. Historical jobs/receipts retain their prior plan and recover without resubmission. Canon, approved assets, other providers and global routing are unchanged.

Functional Turbo, head and identity-edit LoRAs keep their established strengths. Creative adapters connect after these required adapters and before attention, edit patching or sampling. Four-view panels each receive the same selection. Known trigger phrases are added once inside each actual graph text node; `render-prompt.txt` remains the shared creative brief and `comfy-graph.json` is the authority for exact per-node text (including panel camera instructions and triggers). The UI shows selected names, strengths, triggers and reasons in job details and image-version references. ZIP exports include frozen selection, graph and receipt under `local-images/<job-id>/`.

## Owned catalog and sources

Complete metadata/routing is in `workflows/local-images/loras.json`; no external workflow file or network model-card lookup is required at runtime. The runtime only lists available LoRA filenames through local ComfyUI's node schema and uses Studio-owned reviewed metadata. Merely downloading a new file does not make it an automatic candidate; its purpose, family, applicable recipes and preset must be reviewed and added to this catalog.

- Nine Krea style adapters use [Comfy-Org's documented triggers and strength 1.0](https://huggingface.co/Comfy-Org/Krea-2/blob/main/README.md).
- [Krea2 realism V2](https://huggingface.co/RudySen/Krea2-realism-V2) uses 1.0, within the author's documented guidance. No special trigger is injected: the model card's `instance_prompt: none` is interpreted as no trigger, despite the training metadata containing `r3alism`. Its purpose is photographic texture/lighting/expression, not blood expertise.
- [Klein 9B consistency](https://huggingface.co/lrzjason/Consistance_Edit_Lora) requires references. Studio's 0.6 is a conservative trial preset, not an author-recommended number. The source recommends lowering strength when the adapter prevents an edit. Major recomposition/new viewpoints should not automatically acquire a preservation adapter.
- Local `krea2filterbypass3.safetensors` matches the [published file](https://huggingface.co/Sentinel7/krea2/blob/main/2728234/3067151/krea2filterbypass3.safetensors) SHA-256 `ec5901a2d0b8f4e4e1e7e62fe4567566f0837799f7a413b03a06f72f47934dda`: 160 bytes, one F32 `[1,12]` text-fusion projector delta. Studio tested strength 1.0 for non-graphic fictional blood marks on intact cloth. Its automatic eligibility is currently limited to Krea2 Turbo text-to-image and that content use; generic horror, red-color metaphors, negated blood and clean objects are not reasons to apply it. It is not a general new-concept/style LoRA. The sampled improvement is empirical, not an unsupported author claim.
- Other installed NSFW files have no verified blood-use preset here and remain excluded. Krea adapters never route to Klein. The blood adapter is not automatically enabled for the Muse edit model or untested editing recipes.

ComfyUI, model weights/custom nodes and the existing VRAM Manager remain execution dependencies. No automatic download, model replacement, failure fallback or blind GPU retry was added. Filename availability is checked again before submission; the recorded file hash above was verified during acceptance, not rehashed on every generation.

## Acceptance

Evidence is in `data/acceptance/image-auto-lora-20260910/`. All actual images and preparation calls use separate acceptance data and do not adopt or alter user production assets. The first real Krea image automatically selected realism V2 and rendered successfully but failed the requested visible-blood criterion. The same-seed baseline was also too faint. The subsequent same-seed, identical-render-prompt qualification automatically selected the text-fusion adapter plus realism and produced clear dark-red stains. This confirms one bounded blood-mark example, not arbitrary graphic imagery or universal visual quality.

Full tests at implementation baseline: 552 passed. Later validation/export changes: 53 relevant tests passed. Final end-to-end results and deployment details are recorded in verification.json alongside this document's evidence directory.

Final acceptance: full Studio Krea job `5fc5bfb746ab4924` independently selected both matching adapters and rendered clear blood stains. Klein `416fc84e0d6a4f22` selected consistency 0.6 and retained Turbo 0.2, preserving the reference blood pattern/cloth/tray for a subtle cooler-light edit. The final red-color-metaphor vector control chose none with the blood candidate present. Deployed to 4760 with every SQLite table row preserved and integrity ok.
